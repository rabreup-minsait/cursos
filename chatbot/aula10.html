De código funcional a sistema profissional

Agora entra outro recurso muito útil: o FAQ, uma lista de perguntas frequentes com respostas prontas. Se o usuário pergunta horário de atendimento, endereço ou política de troca, não faz sentido gastar IA. A resposta já existe e precisa ser sempre igual. Um dicionário com palavras-chave mapeadas para respostas prontas resolve isso na hora, sem tokens e sem espera.

🙋
Mas e se o dado do FAQ mudar, como atualizo sem alterar o código?

Essa é uma boa observação. Enquanto o FAQ está no código, qualquer mudança exige reiniciar o servidor. Em produção, o ideal é mover essas informações para um arquivo de configuração separado, uma planilha ou um banco de dados. O código lê esses dados ao iniciar, ou os busca a cada requisição. Para o nosso nível atual, o dicionário no código funciona bem e o padrão é o mesmo independente da fonte.

O chatbot que construímos ao longo do curso funciona. Mas funcionar não é o mesmo que ser profissional. Nesta última aula organizamos o que já existe com três práticas que fazem toda a diferença quando o sistema cresce: configuração centralizada, separação de responsabilidades e logs.

Pensa num sistema que funcionou perfeitamente durante semanas e de repente começa a dar respostas estranhas. Você não muda nada, mas algo está diferente. Sem logs, você vai caçar o problema no escuro. Sem configuração centralizada, você vai revisar vinte arquivos tentando lembrar onde ajustou a temperatura. Sem separação de responsabilidades, uma mudança em qualquer lugar pode quebrar outra coisa inesperadamente.

Esses três hábitos não mudam o que o sistema faz. Mudam como ele é mantido, como você encontra problemas e como outra pessoa consegue entender o código que você escreveu.

as três práticas desta aula
1Configuração centralizada: todos os parâmetros do sistema num único arquivo, fácil de ajustar sem tocar na lógica
2Separação de responsabilidades: cada função faz uma coisa só, e cada arquivo tem um papel claro
3Logs: registro de tudo que acontece no sistema, essencial para encontrar bugs e entender o comportamento em produção

Começa pela configuração centralizada. Em todos os exercícios do curso, os parâmetros ficavam espalhados pelo código. A temperatura aqui, o modelo ali, o limite do histórico em outro lugar. Quando você precisa ajustar algo, precisa varrer o arquivo inteiro. Em projetos com múltiplos arquivos, precisa varrer todos. A solução é criar um arquivo separado chamado config.py que reúne todos os parâmetros num único ponto.

🙋
Mas isso não é só mover variáveis de lugar? Qual a diferença na prática?

A diferença aparece quando o sistema cresce. Com configuração centralizada, você ajusta a temperatura de 0.3 para 0.4 em um lugar, e todos os módulos que usam esse parâmetro recebem a mudança automaticamente. Você consegue versionar a configuração separada do código, deixar comentários explicando por que cada valor foi escolhido, e entregar o sistema para outra pessoa com a segurança de que os parâmetros estão documentados num único lugar. Um bug de temperatura incorreta ou modelo errado é encontrado em segundos.

import warnings, urllib3, unicodedata, httpx, os
from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware
from pydantic import BaseModel
from openai import OpenAI
from dotenv import load_dotenv
import config # importa o arquivo de configuracao

warnings.filterwarnings("ignore"); urllib3.disable_warnings(); load_dotenv()

app = FastAPI()
app.add_middleware(CORSMiddleware, allow_origins=["*"], allow_methods=["*"], allow_headers=["*"])
client = OpenAI(api_key=os.getenv("OPENAI_API_KEY"), http_client=httpx.Client(verify=False))

usuarios: dict = {}

def normalizar(t: str) -> str:
    t = unicodedata.normalize("NFD", t.lower())
    return "".join(c for c in t if unicodedata.category(c) != "Mn")

def obter_usuario(uid: str) -> dict:
    if uid not in usuarios:
        usuarios[uid] = {
            "perfil": {"nome": None},
            "mensagens": [{"role": "system", "content": config.SYSTEM_BASE}]
        }
    return usuarios[uid]

class Pergunta(BaseModel):
    texto: str
    user_id: str | None = "default"

@app.get("/")
def raiz(): return {"mensagem": f"{config.NOME_BOT} no ar!"}

@app.post("/chat")
def chat(pergunta: Pergunta):
    uid = (pergunta.user_id or "default").strip()
    u = obter_usuario(uid)
    msgs = u["mensagens"]
    texto = pergunta.texto.strip()
    if not texto: return {"resposta": ""}

    t = normalizar(texto)
    if "meu nome e" in t:
        nome = texto.split("meu nome e")[-1].strip().title()
        u["perfil"]["nome"] = nome
        return {"resposta": f"Prazer, {nome}!"}

    ctx = config.SYSTEM_BASE
    if u["perfil"]["nome"]: ctx += f" O cliente se chama {u['perfil']['nome']}."
    msgs[0]["content"] = ctx
    msgs.append({"role": "user", "content": texto})

    try:
        r = client.chat.completions.create(
            model=config.MODELO,           # usa config
            messages=msgs,
            max_tokens=config.MAX_TOKENS,  # usa config
            temperature=config.TEMPERATURA  # usa config
        )
        resposta = r.choices[0].message.content
    except Exception:
        resposta = "Servico indisponivel."

    msgs.append({"role": "assistant", "content": resposta})
    if len(msgs) > config.LIMITE_HIST:   # usa config
        msgs = [msgs[0]] + msgs[-(config.LIMITE_HIST - 1):]
    u["mensagens"] = msgs
    return {"resposta": resposta}
import configImporta o arquivo de configuração. Qualquer variável definida em config.py fica acessível com config.NOME_VARIAVEL. Os dois arquivos precisam estar na mesma pasta.
config.MODELO
config.TEMPERATURA
config.MAX_TOKENS		Parâmetros lidos da configuração. Para mudar o modelo ou a temperatura, você edita config.py e o efeito se propaga para todo o sistema sem tocar na lógica.
config.LIMITE_HISTLimite do histórico via configuração. O cálculo config.LIMITE_HIST - 1 preserva o system prompt e mantém as últimas mensagens dentro do limite definido.

Exercício 068 - config.py e main.py na mesma pasta

Com a configuração separada, o próximo passo é falar de separação de responsabilidades. O conceito é simples: cada função deve fazer uma coisa só, e o nome dela deve deixar claro o que é essa coisa. Uma função chamada chat() que classifica, busca dados, chama a IA, atualiza o histórico e limita o tamanho está fazendo cinco coisas. Quando algo der errado, você vai precisar ler tudo para descobrir onde está o problema.

A separação não precisa ser rígida desde o começo. O processo natural é: escreve tudo junto para funcionar, depois identifica as responsabilidades, depois extrai em funções. O critério para saber se uma função tem responsabilidade única é conseguir descrever o que ela faz sem usar "e". Se você precisar de "e", ela faz mais de uma coisa.

separação de responsabilidades na prática
◆normalizar(texto) trata o texto para comparação
◆classificar(texto) identifica a intenção
◆buscar_produto(texto) consulta a base de dados
◆montar_system(perfil, dados) constrói o prompt
◆chamar_ia(msgs, temperatura) faz a chamada e retorna texto
◆chat(pergunta) orquestra tudo isso em sequência

Com funções assim organizadas, um bug na busca de produto não afeta a chamada à IA. Uma mudança no prompt não toca na classificação. E quando alguém ler o código pela primeira vez, cada parte fica imediatamente compreensível pelo nome da função.

Pausa para o café!

Levanta, respira, e quando voltar nós adicionamos logs ao sistema.

A última prática desta aula são os logs. Um log é um registro de texto que o sistema grava enquanto roda, descrevendo o que está acontecendo. Quando algo dá errado, o log conta a história: quem enviou a mensagem, qual categoria foi identificada, se a busca retornou resultado, se a IA respondeu ou lançou uma exceção.

O Python tem uma biblioteca nativa chamada logging que cuida disso. Você configura uma vez e usa logging.info() para registrar eventos normais, logging.warning() para situações que merecem atenção e logging.error() para erros. O resultado vai para o terminal e, se você configurar, para um arquivo em disco. Diferente do print(), os logs têm data, hora e nível, o que facilita muito a análise.

🙋
Qual a diferença entre usar print() e logging? Não é a mesma coisa?

O print() funciona, mas não escala. Ele não tem data e hora, não tem nível de gravidade, e você não consegue desligar todas as mensagens de uma vez sem apagar cada linha. Com o logging, você configura o nível mínimo e decide o que aparece. Em produção, mostra apenas erros. Em desenvolvimento, mostra tudo. O conteúdo vai automaticamente para um arquivo que você analisa depois. É a diferença entre um post-it e um diário organizado.

import logging, warnings, urllib3, unicodedata, httpx, os
from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware
from pydantic import BaseModel
from openai import OpenAI
from dotenv import load_dotenv
import config

warnings.filterwarnings("ignore"); urllib3.disable_warnings(); load_dotenv()

# configuracao do sistema de logs
logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s [%(levelname)s] %(message)s",

app = FastAPI()
app.add_middleware(CORSMiddleware, allow_origins=["*"], allow_methods=["*"], allow_headers=["*"])
client = OpenAI(api_key=os.getenv("OPENAI_API_KEY"), http_client=httpx.Client(verify=False))

PRODUTOS = {
    "notebook pro":    {"preco": "R$ 4.500", "estoque": "disponivel"},
    "mouse sem fio":   {"preco": "R$ 120",   "estoque": "disponivel"},
    "teclado mecanico":{"preco": "R$ 350",   "estoque": "esgotado"},

    return "".join(c for c in t if unicodedata.category(c) != "Mn")

def classificar(texto: str) -> str:

    if any(g in t for g in ["meu nome"]):  return "dados_usuario"
    if any(g in t for g in ["preco", "estoque", "notebook", "mouse", "teclado"]):  return "produto"

def buscar_produto(texto: str) -> str:

    if not r:
        logger.warning(f"Produto nao encontrado para: {texto}")

def montar_system(perfil: dict, dados: str = "") -> str:

    try:
        r = client.chat.completions.create(
            model=config.MODELO, messages=msgs,
            max_tokens=config.MAX_TOKENS, temperature=temp
        )
        texto = r.choices[0].message.content
        logger.info(f"IA respondeu: {texto[:60]}...")
        return texto
    except Exception as e:
        logger.error(f"Erro na chamada a IA: {e}")
        return "Servico indisponivel."

def atualizar_historico(msgs: list, role: str, texto: str) -> list:
    msgs.append({"role": role, "content": texto})
    if len(msgs) > config.LIMITE_HIST:
        msgs = [msgs[0]] + msgs[-(config.LIMITE_HIST - 1):]

def obter_usuario(uid: str) -> dict:
    if uid not in usuarios:
        usuarios[uid] = {"perfil": {"nome": None},
                          "mensagens": [{"role": "system", "content": config.SYSTEM_BASE}]}
        logger.info(f"Novo usuario criado: {uid}")
    return usuarios[uid]

class Pergunta(BaseModel):
    texto: str; user_id: str | None = "default"

@app.get("/")
def raiz(): return {"mensagem": f"{config.NOME_BOT} no ar!"}

@app.post("/chat")
def chat(pergunta: Pergunta):
    uid = (pergunta.user_id or "default").strip()
    u = obter_usuario(uid)
    texto = pergunta.texto.strip()
    if not texto: return {"resposta": ""}

    cat = classificar(texto)
    logger.info(f"[{uid[:8]}] categoria={cat} | msg={texto[:50]}")

    if cat == "dados_usuario":
        t = normalizar(texto)
        if "meu nome e" in t:
            nome = texto.split("meu nome e")[-1].strip().title()
            u["perfil"]["nome"] = nome
            logger.info(f"[{uid[:8]}] nome registrado: {nome}")
            return {"resposta": f"Prazer, {nome}!"}

    msgs = atualizar_historico(msgs, "user", texto)
    resposta = chamar_ia(msgs, temp)
    msgs = atualizar_historico(msgs, "assistant", resposta)

logging.basicConfig(...)Configuração única na inicialização. Define o formato das mensagens com data e hora, o nível mínimo a registrar e os destinos: terminal e arquivo em disco.
logger.info(...)Registra eventos normais. Novo usuário criado, categoria identificada, resposta da IA. Com data e hora automáticas, você consegue reconstruir o que aconteceu numa conversa.
logger.warning(...)Registra situações que merecem atenção. Produto não encontrado não é um erro, mas vale saber com que frequência acontece para melhorar as palavras-chave.
logger.error(...)Registra falhas. Quando a chamada à IA lança uma exceção, o erro vai para o log com a descrição completa do problema, sem aparecer para o usuário.

Sistema com config, separação de funções, logs e front-end reunindo tudo do curso desafio

Crie os arquivos config.py, 073_Exercicio.py e 073_index.html do zero, para um tema à sua escolha. O sistema deve reunir tudo o que foi construído no curso.

  1. config.py com todos os parâmetros: modelo, temperaturas, max_tokens, limite do histórico, nome do bot, system prompt e configurações de log
  2. Funções com responsabilidade única: normalizar, classificar, buscar dados, montar system, chamar IA, atualizar histórico, obter usuário
  3. FAQ com pelo menos cinco entradas sem acionar a IA
  4. Base de dados local com pelo menos quatro entradas e busca com injeção no prompt
  5. Logs com logging.info, logging.warning e logging.error nos pontos certos
  6. Separação por user_id com dicionário de usuários e rota /limpar
  7. Front-end com crypto.randomUUID(), fetch() e async/await
  8. CORS habilitado, chave via os.getenv(), todo erro tratado com try/except

💡 Dica: construa do zero. O exercício anterior tem uma boa base para consultar, mas escrever cada parte é o que consolida.

O arquivo completo 073_Exercicio.py está disponível para download, com todas as camadas implementadas e logs em cada ponto relevante do fluxo. O config.py de exemplo também está disponível.
